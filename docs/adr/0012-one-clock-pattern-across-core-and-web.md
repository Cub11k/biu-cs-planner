# One clock pattern across core and web

A clock string is `hh:mm`, zero-padded, `00:00` through `23:59` — one pattern, `/^([01]\d|2[0-3]):[0-5]\d$/`, written identically wherever a clock is read or validated. The schemas decide what a clock string is; no reader holds a looser opinion than the schema that admitted the data it reads.

Five files carry that pattern and none of them varies it: `core/src/state/schema.ts`, `core/src/catalog/schema.ts`, `core/src/shoham/dialect.ts`, `web/src/timetable/week.ts`, and — since this decision — `core/src/clock.ts`. It is written five times rather than once because `web` never imports `core` ([ADR-0002](0002-domain-behind-http-api-thin-ui.md)) and the schemas are the contract, not a derivation of it; `fixtures/clock-ranges.json` is the table both *readings* are tested against so that a change to either fails a test instead of drifting quietly (issue #48).

Keeping the five spellings equal is therefore a judgement made in review, not a guarded invariant: the fixture pins `core/src/clock.ts` against `web/src/timetable/week.ts`, and nothing compares the three schema copies to anything. A test that reads the five files and asserts one distinct pattern would close that, and is worth its own ticket.

`core/src/clock.ts` used to read `/^(\d{1,2}):([0-5]\d)$/`, a pattern inherited from the Clashes module, and so read `"9:00"` where every schema and `web` refused it. The reason given was that comparing clock strings directly is only correct while every one of them is zero-padded — `"9:00"` sorts after `"10:00"`, so a Clash would be hidden rather than reported — and a Blocked Time is student-entered. Narrowing the pattern dissolves that worry rather than answering it: within the padded set the strings sort chronologically anyway, so the trap needs no defence. Reading minutes stays, for the reason it was always really needed — an overlap is arithmetic on two ranges, and an `end` of `"00:00"` is 1440, a value no comparison of strings can produce.

What does not survive is *accepting* the unpadded spelling, which every schema admitting a span refuses first: `blockedTimeSchema` and `pickedMeetingSchema` in a State File, `meetingSchema` in a Catalog, `isClockTime` in the Shoham dialect. The ticket put it as a guard "against data the type system says cannot arrive"; strictly it is the schemas and not the types that refuse it — `WeeklySpan`'s `start` and `end` are plain `string`, a structural contract anything can satisfy, and `findMeetingClashes` is exported — so the guarantee is a validated path, not a compiled one. Either way the two halves of the app held opposite opinions about whether the defence was needed, which is what issue #54 exists to settle.

**Consequence, deliberately accepted: if an unpadded time can ever arrive, that is a schema bug to fix at the schema.** Not a reading to widen, and not a repair at the reader. A time the pattern refuses is read as no time at all, which keeps it out of every Clash rather than letting it collide with whatever encloses it — and nothing is blocked either way.

The consequence is accepted with its cost named: only the State File path reports such a time, and it reports it as `blocked-time-does-not-advance`, which is the wrong Warning for "the clock could not be read". Inside the Clashes module an unreadable span produces no Warning at all — it simply Clashes with nothing. So a schema bug of this kind would surface as a Meeting silently taking part in no Clash, which is the price of having one pattern instead of a reader that second-guesses it.

Two tests encoded the removed defence and were rewritten to assert the refusal instead: `core/src/timetable/clashes.test.ts` on a Blocked Time, and `core/src/shoham/overlaps.test.ts` on two Meetings of one Group. The second already said in its own comment that no current path produces an unpadded time; the first asserted the old reading without a reason, and now carries one.

## Considered Options

- **Widen `web` to match `core`:** both would accept `"9:00"`. It keeps a defence nothing needs and pays for it by making `web` read data *looser* than the API that validated it — the grid would place a time the State File it came from would have refused to store. It also leaves the pattern spelled two ways across five files, which is the drift issue #48 exists to stop.
- **Keep both readings and record the asymmetry:** put an unpadded range in `fixtures/clock-ranges.json` asserting that `core` is deliberately forgiving where `web` is strict, turning a drift into a recorded intent. Rejected because the intent is not one worth holding: a Blocked Time of `"9:00"`–`"11:00"` would Clash correctly in `core` and be drawn nowhere by `web`, and writing that down makes it permanent rather than fixed. The table now states no difference, and no unpadded row was added.
