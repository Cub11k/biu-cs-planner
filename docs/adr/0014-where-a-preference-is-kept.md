# A Device Preference is kept in the browser's store; a preference about the person or the document is kept in the State File

**Per-device display preference → the browser's own store. Preference about the person or the document → the State File.** #114 ruled this for the colour scheme and PR #137 built it, but the rule is wider than the ticket it was ruled in and it is what #115 has to cite. Until now it was discoverable only from a header comment in `web/src/scheme.ts`, a merged pull request body, and one widened sentence in [ADR-0003](0003-workspace-folder-is-source-of-truth.md) whose own decision is about something else. This records the decision that was made; it does not re-open it.

A colour scheme is the first kind, and the argument is not that sharing one would be inconvenient. The same Plan opened on a phone in the sun and on a desktop at night wants different answers, so a State File carrying a scheme would be **wrong on the second device** rather than merely unhelpful — a document that travels cannot know which screen is reading it. A language is the other kind: a Hebrew speaker wants Hebrew on every device they own, and `settingsSchema` in `core/src/state/schema.ts` already holds it beside `examSpacingDays`, as `docs/design.md`'s Workspace screen has listed since the design was agreed. The distinction is not "big things in files, small things in the browser": it is whose property the value is.

What it costs to be wrong differs the same way. A preference about the person or the document is data about them, and belongs where [ADR-0003](0003-workspace-folder-is-source-of-truth.md) puts data — a file in the Workspace that backs up, syncs and survives a browser reset. A Device Preference has no such claim: losing it costs one click, and carrying it between devices is its failure mode rather than its feature.

Every preference the app has today, on one side or the other:

- **Colour scheme — the browser.** `localStorage`, under `biu-cs-planner.scheme` (`web/src/scheme.ts`). It belongs to the screen and the room the screen is in. Nothing in the app reads it as a value: it becomes a `data-theme` attribute on `<html>` and `web/src/index.css` does the rest.
- **Language — the State File**, `settings.language`. It belongs to the person, on every device.
- **Exam spacing — the State File**, `settings.examSpacingDays`. It belongs to the document, and a domain check reads it.
- **The Launch Token — the browser, and it is not a preference.** It is in this list because it is the other thing the browser's store holds, and the rule must not be read as covering it: nothing about it is a choice. It is there because a URL fragment has to be caught and reused (`web/src/token.ts`), and [ADR-0004](0004-localhost-auth-bearer-token.md) is where it is decided.

**The accepted cost: a different port forgets.** `localStorage` is per origin and an origin includes the port, which `web/src/token.ts` already names for the token. The default port is 8900 and a taken one is not an error — `onAFreePort` in `server/src/port.ts` walks upward to the first free port, up to twenty. So a student who chose dark, and whose next run lands on 8901, opens a page that **follows their operating system again**; one use of the control puts it back, and each port then remembers its own answer independently.

What makes that acceptable is *what* it degrades to. The forgotten state is the no-choice state, and `web/src/scheme.ts` and `web/src/index.css` are built so that no-choice is a single state rather than a third palette: no `data-theme` attribute on `<html>`, the `prefers-color-scheme` media query decides, and the page is exactly the one every student had before #114. It is un-personalised, never wrong and never broken. The same accident to a store holding a Pick or a Variant would lose work — that asymmetry is the rule's reason and not a lucky detail, which is why this ADR is about *where a preference* is kept and never widens to data. The code gives every way of not knowing the same answer for the same reason: an unrecognised stored value, a browser with storage switched off entirely, and a render with no browser at all are all "never told" (`storedScheme` and `schemeStore` in `web/src/scheme.ts`).

## Considered Options

- **The State File, for the scheme as well**, so that one place holds every preference and a preference backs up and syncs like everything else. Rejected for the reason above — it would be wrong on the second device — and it buys that wrongness at a price: the State File schema, the save path, #90's external-edit guard and [ADR-0013](0013-undo-is-snapshots-not-commands.md)'s `settings excluded` undo rule, all for a value no domain check ever reads and a stylesheet consumes from an attribute.
- **`sessionStorage`, or keeping the choice only for the life of the page.** Rejected: it reverts on *every* reload, which is strictly more forgetting than a port change, for the same amount of code.
- **A per-device store served by the server**, keyed on something stabler than an origin — the server's own config directory does not move when the port does, which is exactly why the Launch Token file lives there ([ADR-0004](0004-localhost-auth-bearer-token.md)). This is the one option that removes the cost above entirely, and #114's implementer raised it as such. **Not taken now, and not decided here.** It needs answers this decision has no standing to give: what identifies a *device* to a server that every device reaches over loopback as `127.0.0.1`, whether the unit is a device or a browser profile, whether such a preference travels through the API ([ADR-0002](0002-domain-behind-http-api-thin-ui.md)) and what the page shows before it has an answer. That is a design decision rather than an implementation, and what it buys out is one click after a port change. It is recorded here so that whoever wants it starts from an option already on the table.

## Consequences

- **A new preference is placed before it is built.** The question is "the device, or the person and the document?", it has one answer per preference, and the list above is where that answer is written down. A preference added later extends the list.
- **#115 puts the language in the State File**, as the design already says, rather than following the scheme into `localStorage`. It still owes a separate answer for the screens that render before any State File is open — the unauthorized notice and the Workspace picker — where nothing in the Workspace can hold a language yet. **That is not ruled here.** A pre-Workspace fallback in the browser would not make the browser the language's home, and deciding what it should be belongs to #115.
- **ADR-0003 stops carrying the rule.** Its sentence says only that the browser holds no data — the Launch Token and Device Preferences are not data — and points here for where a preference goes.
- **A Device Preference is `web`'s alone and never crosses the API.** The scheme reaches no server and appears in no response; a State File preference arrives through the API like everything else it holds. So the two kinds are not interchangeable at the cost of one field: moving a preference across the line means the save path in one direction and a migration in the other, which is why this is an ADR and not a comment.
- **Undo covers neither kind.** [ADR-0013](0013-undo-is-snapshots-not-commands.md) keeps settings out of the stack because undoing a Pick must not flip the UI language, and a Device Preference is not in the document at all. A preference is put back by the control that set it.
- **A browser reset loses the Device Preferences and nothing else**, which is [ADR-0003](0003-workspace-folder-is-source-of-truth.md)'s promise restated rather than an exception to it.
- **Two tabs on one origin need not agree.** The control reads the store once as it mounts and nothing listens for a `storage` event, so a second open tab keeps the scheme it loaded with until it is reloaded. Acceptable for the same reason the port hazard is — the disagreement is between two screens about a property of a screen, and neither tab is wrong about the document.
