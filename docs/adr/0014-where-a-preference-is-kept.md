# Where a preference is kept: the device's in the browser, the person's and the document's in the State File

**Per-device display preference → the browser's own store. Preference about the person or the document → the State File.** #114 ruled this for the colour scheme and PR #137 built it, but the rule is wider than the ticket it was ruled in and it is what #115 has to cite. Until now it was discoverable only from a header comment in `web/src/scheme.ts`, a merged pull request body, and one widened sentence in [ADR-0003](0003-workspace-folder-is-source-of-truth.md) whose own decision is about something else. This records the decision that was made; it does not re-open it.

A colour scheme is the first kind, and the argument is not that sharing one would be inconvenient. The same Plan opened on a phone in the sun and on a desktop at night wants different answers, so a State File carrying a scheme would be **wrong on the second device** rather than merely unhelpful — a document that travels cannot know which screen is reading it. A language is the other kind: a Hebrew speaker wants Hebrew on every device they own, and `settingsSchema` in `core/src/state/schema.ts` already holds it beside `examSpacingDays`, as `docs/design.md`'s Workspace screen has listed since the design was agreed. The distinction is not "big things in files, small things in the browser": it is whose property the value is, and so what it costs to be wrong. A preference about the person or the document is data about them and belongs where [ADR-0003](0003-workspace-folder-is-source-of-truth.md) puts data — a file in the Workspace that backs up and syncs. A Device Preference has no such claim: losing it costs one click, and carrying it between devices is its failure mode rather than its feature.

Every preference the app has today, on one side or the other. The colour scheme is built and behaves this way; the other two are the design's placement, which `core`'s schema holds and #115 wires — the rule is the same either way, and what the code has reached is not what decides it:

- **Colour scheme — the browser.** `localStorage`, under `biu-cs-planner.scheme` (`web/src/scheme.ts`). It belongs to the screen and the room the screen is in. No domain check reads it, and beyond the control that sets it nothing reads it as a value at all: it becomes a `data-theme` attribute on `<html>` and `web/src/index.css` does the rest.
- **Language — the State File**, `settings.language` (`core/src/state/schema.ts:146`). It belongs to the person, on every device.
- **Exam spacing — the State File**, `settings.examSpacingDays`. It belongs to the document, and a domain check is built to read it: `checkExams` in `core/src/timetable/exams.ts` takes a `spacingDays` threshold, though nothing yet carries the field to it — that wiring is #115's along with the language.
- **The Launch Token — the browser, and it is not a preference.** It is listed because it is the other thing that store holds and the rule must not be read as covering it: nothing about it is a choice. It is there because a URL fragment has to be caught and reused (`web/src/token.ts`), and [ADR-0004](0004-localhost-auth-bearer-token.md) decides it.

**The accepted cost: a different port forgets.** `localStorage` is per origin and an origin includes the port, which `web/src/token.ts` already names for the token. The default port is 8900 and a taken one is not an error — `onAFreePort` in `server/src/port.ts` walks upward to the first free port, up to twenty. So a student who chose dark, and whose next run lands on 8901, opens a page that **follows their operating system again**; one use of the control puts it back, and each port then remembers its own answer independently. The Launch Token sits behind the same origin and loses the same way, and the difference is the point: the launcher prints a URL carrying the token, so a moved port re-delivers it as a matter of course. Nothing re-delivers a scheme — a Device Preference is the value on that origin with no second source.

What makes that acceptable is *what* it degrades to. The forgotten state is the no-choice state, which `web/src/scheme.ts` and `web/src/index.css` keep a single state rather than a third palette: no `data-theme` attribute on `<html>`, the `prefers-color-scheme` media query decides, and the page is the one every student had before #114 — un-personalised, never wrong. The same accident to a store holding a Pick or a Variant would lose work, and that asymmetry is the rule's reason rather than a lucky detail: this is about *where a preference* is kept and never widens to data. The code gives every way of not knowing that one answer — an unrecognised value, storage switched off, and a render with no browser at all are all "never told" (`storedScheme` and `schemeStore`).

## Considered Options

- **The State File, for the scheme as well**, so that one place holds every preference and a preference backs up and syncs like everything else. Rejected for the reason above — it would be wrong on the second device — and it buys that wrongness at a price: the State File schema, the save path, #90's external-edit guard and [ADR-0013](0013-undo-is-snapshots-not-commands.md)'s `settings excluded` undo rule, all for a value no domain check ever reads and a stylesheet consumes from an attribute.
- **`sessionStorage`, which bounds the choice by the tab.** Rejected as strictly more forgetting than a port change, for the same amount of code: it survives a reload but not a new tab or a new window, so a student who opens the planner from their bookmark twice gets asked twice, on the one port where nothing went wrong. (#137's body said "reverts on *every* reload", which is not what `sessionStorage` does; the rejection stands on the fact above instead.)
- **A per-device store served by the server**, keyed on something stabler than an origin — a file beside the Launch Token's in the user config directory does not move when the port does, which is a property of that location rather than the reason [ADR-0004](0004-localhost-auth-bearer-token.md) chose it. This is the one option that removes the cost above entirely, and #114's implementer raised it as such. **Not taken now, and not decided here.** It needs answers this decision has no standing to give: what identifies a *device* to a server that every device reaches over loopback as `127.0.0.1`, whether the unit is a device or a browser profile, whether such a preference travels through the API ([ADR-0002](0002-domain-behind-http-api-thin-ui.md)) and what the page shows before it has an answer. That is a design decision rather than an implementation, and what it buys out is one click after a port change. It is recorded here so that whoever wants it starts from an option already on the table.

## Consequences

- **A new preference is placed before it is built**, by one question — the device, or the person and the document? — and the list above is where the answer is written down. A preference added later extends it.
- **#115 puts the language in the State File**, as the design already says, rather than following the scheme into `localStorage`. Its criterion "the PR says whether a language is per document or per person, and how that agrees with #114" is answered by citing this ADR rather than by re-deciding it. Two things it asks are deliberately **not** ruled here: what the first paint does before any State File has been read, and whether `navigator.language` seeds a first run — a guess about a person is not a preference they expressed, so the rule above does not place it. A pre-Workspace fallback in the browser would not make the browser the language's home either way.
- **ADR-0003 stops carrying the rule.** Its sentence says only that the browser holds no data — the Launch Token and Device Preferences are not data — and points here for where a preference goes.
- **A Device Preference crosses no API today.** The scheme reaches no server and appears in no response, and `server/src/api.ts` carries no settings route at all; when #115 adds one, what travels over it is a State File preference. That is a fact about the scheme rather than a rule for the category — the server-served store above is exactly the case where a Device Preference would use an API, and this ADR leaves it open. What the rule does fix is that the two kinds are not interchangeable at the cost of one field: moving a preference across the line means the save path in one direction and a migration in the other, which is why this is an ADR and not a comment.
- **Undo covers neither kind.** [ADR-0013](0013-undo-is-snapshots-not-commands.md) keeps settings off the stack so that undoing a Pick cannot flip the UI language, and a Device Preference is not in the document at all. A preference is put back by the control that set it.
- **A browser reset loses the Device Preferences and no data.** It loses the Launch Token with them, which the next launch delivers again in the URL it prints ([ADR-0004](0004-localhost-auth-bearer-token.md)). Both are restored by an action a student takes anyway; the Workspace is untouched, which is [ADR-0003](0003-workspace-folder-is-source-of-truth.md)'s promise restated rather than an exception to it.
- **Two tabs on one origin need not agree, and whether that is acceptable is not decided here.** It follows from the store rather than from the rule: the control reads the store once as it mounts and nothing listens for a `storage` event, so a second open tab keeps the scheme it loaded with until it is reloaded. #137's reviewers raised it and #137 recorded it as unaddressed and outside its ticket, which is where it still stands — this ADR notes the behaviour so that a ticket taking it up has it written down, and rules nothing about it. What can be said is the cheap half: a stale tab shows a scheme that was chosen rather than a wrong page, and neither tab is wrong about the document, because the document is not what this store holds.
